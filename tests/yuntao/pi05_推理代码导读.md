## 全景：一次推理到底发生了什么

```text
 evaluate_bi.py（30Hz 主循环）
   │
   ├─ ① robot.get_observation()            ← alohamini_client.py
   │      ZMQ 5556 → Host → 读串口+相机 → JPEG 回传 → 解码成 numpy
   │
   ├─ ② robot_observation_processor(obs)   ← processor/
   │      dict 规整成 EnvTransition
   │
   ├─ ③ engine.get_action(obs_frame)       ← rollout/inference/{sync,rtc}.py
   │      ├─ preprocessor(obs)             ← 归一化 / rename / 分词 / state→提示词
   │      ├─ policy.predict_action_chunk   ← pi05/modeling_pi05.py
   │      └─ postprocessor(actions)        ← 反归一化 + 相对动作还原成绝对关节角
   │
   ├─ ④ ActionInterpolator                 ← utils/action_interpolator.py
   │      把 1 个动作插值成 N 个，提高下发频率
   │
   └─ ⑤ robot.send_action(action)          ← alohamini_client.py
          ZMQ 5555 → Host 50Hz 控制环 → Feetech 总线 → 舵机
```

**关键认知**：策略（③）只吐**关节目标值**，不直接碰硬件；
真正驱动舵机的是树莓派上 50 Hz 的 Host 循环。中间靠两个 ZMQ 端口解耦。

## ③ 推理引擎：`src/lerobot/rollout/`

这一层是「策略 ↔ 机器人」的胶水，**最值得先读的是 sync（122 行）**。

| 文件 | 行数 | 作用 |
|---|---|---|
| `inference/factory.py` | 128 | `create_inference_engine()`，按 `sync` / `rtc` 分叉 |
| `inference/sync.py` | 122 | **同步**：每 tick 调 `policy.select_action`；它内部维护 50 步动作队列，队列空时才真推理一次 |
| `inference/rtc.py` | 361 | **异步（RTC）**：后台推理下一块，用 prefix inpainting 与正在执行的那块拼接 |
| `robot_wrapper.py` | 79 | `ThreadSafeRobot`，给推理线程加锁访问 robot |
| `configs.py` / `ring_buffer.py` / `strategies/` | — | RTC 的队列与拼接策略 |

**sync 的核心就 4 行**（`sync.py:110–121`）：

```python
observation = prepare_observation_for_inference(observation, self._device, self._task, self._robot_type)
observation = self._preprocessor(observation)   # 观测 → 模型输入
action = self._policy.select_action(observation)  # 模型 → 单个动作
action = self._postprocessor(action)              # 反归一化 + 相对→绝对
```

> 注意：**preprocessor / postprocessor 在调用 policy 之前/之后**，不在模型内部。
> 这也是当初 `verify_pi05_inference.py` 踩坑的地方（漏了 preprocessor → 键名对不上）。

**`select_action` 和 `predict_action_chunk` 的关系**（`modeling_pi05.py`）：

| 方法 | 行 | 行为 |
|---|---|---|
| `select_action(batch)` | 1221 | 维护 `_action_queue`；**队列空时**才 `predict_action_chunk()` 补 50 步，然后每次 `popleft()` 一个。开头有断言：**RTC 开启时不能用它** |
| `predict_action_chunk(batch, **rtc_kwargs)` | 1238 | 直接跑一次模型，返回 `(B, 50, 7)` 整个动作块 |

所以 **sync 不是每 tick 都推理**：它一次推理吃 50 个 tick（=1.67 s @30fps），
队列吃空的那一下会阻塞一次完整推理 —— 这就是 sync 卡顿的来源。RTC 则把这个阻塞挪到后台线程。

**读完应能回答**
- `sync` 为什么只有「第一个动作」被用掉？其余 49 个呢？
- RTC 的 `queue_threshold` / `execution_horizon` 分别控制什么？
- 为什么 `use_relative_actions=true` 时必须走 RTC？（绝对目标会随动作块漂移）

## ④ 模型：`src/lerobot/policies/pi05/`

### `configuration_pi05.py`（175 行）

`PI05Config`：`chunk_size=50`、`n_action_steps=50`、`max_state_dim=32`、`max_action_dim=32`、
`num_inference_steps=10`、`use_relative_actions`、`relative_exclude_joints=["gripper"]`。
**checkpoint 里的 `config.json` 就是它的序列化**，先读它比读模型省力。

### `modeling_pi05.py`（1304 行）——分三块读，别从头读

**第 1 块：结构**（344–560）
`PaliGemmaWithExpertModel`：PaliGemma-2B（VLM，冻结）+ Gemma-300M（action expert）。
⚠️ 375/383/391 行显式写死 `dtype="float32"` —— 这就是加载内存峰值 18.3 GB 的原因。

**第 2 块：算法**（563–910）
`PI05Pytorch.embed_prefix()`（653）把图像 + 语言 token + **state 量化后的 token** 拼成前缀；
`sample_actions()`（792）是 **flow matching** 去噪：从噪声出发，`num_inference_steps=10` 步生成 50 步动作块。

**第 3 块：对外接口**（911–1304）
`PI05Policy._preprocess_images()`（1149）：**键名必须叫 `observation.images.base_0_rgb` 等**，
缺的图会补零 mask；`predict_action_chunk()`（1238）是引擎调用的入口。

**读完应能回答**
- 50 步动作块是怎么一次生成的？（10 步去噪，每步对整段 50 步并行去噪）
- 为什么训练用 2 路相机、模型却要 3 路输入？（`left_wrist_0_rgb` 缺席 → mask=0）
- state 是作为向量喂进网络吗？（不是，见下一节）

### `processor_pi05.py`（179 行）

`Pi05PrepareStateTokenizerProcessorStep`（53）—— **π0.5 的核心魔法**：

```
Task: pickup1, State: 227 101 164 202 132 180 9; Action: 
```

把 7 维 state 用 256 个 bin **离散化成文字**，拼进提示词。所以：
**state 超出训练分布 → bin 饱和到 0/255 → 模型看到没见过的输入 → 输出跑飞。**
这就是 Runbook §4.2「每集必须回到起始姿态」的代码级原因。

## ⑤ 处理器：`src/lerobot/processor/` + `src/lerobot/policies/factory.py`

preprocessor 是一条流水线，顺序在 `policy_preprocessor.json` 里能看到且**已存进 checkpoint**：

| 顺序 | 步骤 | 作用 |
|---|---|---|
| 1 | `RenameObservationsProcessorStep` | `observation.images.forward` → `base_0_rgb`（训练时的 `--rename_map`） |
| 2 | `AddBatchDimensionProcessorStep` | 加 batch 维 |
| 3 | `RelativeActionsProcessorStep` | 绝对动作 → 相对动作（**gripper 除外**） |
| 4 | `NormalizerProcessorStep` | 用 q01/q99 归一化到 [-1,1] |
| 5 | `Pi05PrepareStateTokenizerProcessorStep` | state → 提示词里的 bin |
| 6 | `TokenizerProcessorStep` | PaliGemma 分词 |
| 7 | `DeviceProcessorStep` | 搬上 GPU |

postprocessor 反着来：`Unnormalizer` → `AbsoluteActionsProcessorStep`（相对 → 绝对）。

**入口**：`src/lerobot/policies/factory.py` 的 `make_pre_post_processors(...)`（731 行文件里的核心函数）。
它会把 `RelativeActionsProcessorStep` 和 `AbsoluteActionsProcessorStep` **重新配对**
（`_reconnect_relative_absolute_steps`），否则推理时无法把相对动作还原。

**读完应能回答**
- 为什么 `--rename_map` 不用再传？（已存进 checkpoint 的 `policy_preprocessor.json`）
- 归一化统计量从哪来？（checkpoint 里的 `policy_preprocessor_step_3_normalizer_processor.safetensors`）
- gripper 为什么不参与相对动作？

## 一句话总结每层职责

| 层 | 文件 | 一句话 |
|---|---|---|
| 调度 | `evaluate_bi.py` | 30 Hz 循环：取观测 → 推理 → 插值 → 下发 → 记录 |
| 通信 | `alohamini_client.py` / `alohamini_host.py` | 两个 ZMQ 端口把「算」和「动」解耦到两台机器 |
| 安全 | `alohamini.py` | 限位、过载、堵转、看门狗，全在 Host 侧兜底 |
| 引擎 | `rollout/inference/*` | preprocessor → policy → postprocessor，sync/RTC 两种节奏 |
| 模型 | `policies/pi05/*` | PaliGemma + 300M expert，flow matching 一次出 50 步 |
| 处理器 | `processor/*` | 键名、归一化、相对动作、state→提示词 |
